# 函数调用性能优化计划

## 文档说明

本计划分为两部分：步骤一至五保留已经完成的局部优化及历史测量；步骤六至十三作为 `plan_compile_time_optimization.md` 执行完毕后的后续行动参考。后续排序依据剩余热点、影响范围和语义风险，不预设提速倍数，也不要求依次完成所有候选项。

状态分为“已完成”“由其他计划承接”“条件执行”“场景驱动”和“暂缓”。“条件执行”表示只有前置优化验收完成且 profiling 仍指向对应热点时才可独立实施；“场景驱动”表示必须由真实异步任务、静态脚本或并行吞吐需求触发；“暂缓”表示不在当前后续路线中直接实施。

当前执行范围：

- 暂无。步骤一至五已完成，不再继续增加缺少热点证据的局部微调。
- 步骤六、七由 `plan_compile_time_optimization.md` 承接，不在本文件中重复实施。
- 步骤五的调用者上下文精简和调用帧存储合并继续暂缓。
- 编译期计划全部验收前，不启动本文后续的结构性改造；如果其真实游戏验收没有改善，停止扩大到新的执行模型。

后续每个候选都应单独建立基线、实现、测试、测量并决定保留或撤回。编译期计划中已保留、撤回或尚未确认的内容，以其最终记录为准，不因本文仍列有候选项而重复实施。

通用原则：

- 保持脚本结果、闭包、默认值、命名参数、外部绑定和异步行为正确。

## 步骤三（已完成）：缓存调用点静态元数据

完成日期：2026-11-02。

影响范围：解释器调用点和字节码模块，不改变字节码格式、函数参数绑定方式或执行模型。

### 已完成内容

- 以调用指令偏移为 key，在每个 `HTBytecodeModule` 中懒缓存 `HTCallSiteInfo`：命名参数名称、位置参数数量、spread 标记、nullable、构造调用标记、对象名称和解码后的 `nextIp`。
- 首次执行调用点时正常解码，后续读取缓存并跳过静态字节，减少重复字符串读取、标志解码和 spread 标记列表分配。
- 参数值、callee、命名参数 map 和位置参数列表仍在每次调用时生成，不缓存调用结果、receiver、闭包或默认值。
- 每个模块独立记录缓存项数量、命中和未命中次数。相同字节码重复执行可复用缓存，新模块实例不复用旧缓存。
- 新增模块重复执行、相同偏移不同命名参数的模块隔离、默认值副作用、构造调用、省略参数、闭包和字段初始化回归测试。
- 参数绑定元数据方案经过独立实现和测量后撤回，详见本节末尾。

### 缓存生命周期与验证

缓存只在调用点首次执行时增加一个 `HTCallSiteInfo` 和一个 map entry；命名参数键列表和位置参数标记列表也只在该时刻分配。没有加载期全量预解码，额外内存与已执行过的静态调用点数量成正比，生命周期与所属模块一致。

专项测试中，5 次执行产生 3 个缓存项、3 次未命中和 12 次命中，命中率为 80%；相同字节码重新执行两次后累计为 18/21 次命中。模块隔离测试使用相同布局但不同命名参数的模块，结果正确。全量 `dart test` 共 446 项通过；修改文件的 `dart analyze` 无问题；JIT/AOT 性能脚本均实际执行且校验值正确。

## 步骤四（已完成）：减少外部对象包装、方法解析和宿主边界成本

完成日期：2026-11-02。

影响范围：外部绑定运行时，不改脚本字节码、函数参数绑定或执行模型。各候选项均独立实现和测量，未整体一次性改造。

### 保留的实现

- 每个解释器持有一个 `Expando<HTExternalInstance>`，复用普通外部对象及 List、Set、Map 等集合的包装器，不阻止对象回收。
- 普通对象命中缓存时直接跳过 reflection 和包装器初始化；数字、字符串、布尔、BigInt、record 和 `Expando` 自身继续使用独立包装器，不进入缓存。
- 包装器记录创建时的 namespace，仅在当前 namespace 相同的情况下复用，避免跨模块或同名类声明误用。重绑 external class 或 reflection 时替换 `Expando`。
- 缓存只保存包装器，不保存属性值或绑定动态返回的方法闭包；属性修改、继承和动态方法绑定继续走原路径。
- raw Dart 函数在无命名参数时，对 0 至 4 个位置参数直接调用；实例方法直接前置 receiver。其他签名和命名参数继续使用 `Function.apply` 及原有定长列表。
- 新增 `typedef_callback` 和 `list_property` 基准，以及继承、动态绑定、模块隔离、receiver 隔离、reflection 失效、集合与基本类型、raw 参数数量和命名参数回退测试。

### 已撤回或未实施的候选

- `Type -> typeString` 缓存：独立收益处于噪声范围，并引入实例无关 reflection 的额外约束，已撤回；包装器命中路径现在会直接跳过 reflection。
- 外部成员声明缓存：单层成员查找与 map 缓存成本接近，独立收益不足且增加声明生命周期复杂度，已撤回。
- typedef 回调 map 缓存：`typedef_callback` JIT 从 171.751 ms 变为 174.068 ms，AOT 从 200.150 ms 变为 207.320 ms；直接保存在 `HTFunction` 上的版本进一步变为 JIT 186.690 ms、AOT 209.902 ms，两种方案均已撤回。
- 内建类型无状态适配器：没有实施。集合使用同一 `Expando` 即可获得包装复用，基本类型也不需要引入共享 receiver 状态的适配器。
- 真实游戏批量绑定 API：当前仓库没有对应游戏场景，未虚构 API 或收益，留待真实项目另行评估。

全量 `dart test` 共 451 项通过；修改文件的 `dart analyze` 无问题；JIT/AOT 基准均实际执行且校验值正确。热点循环中的包装器命中、不同 receiver、模块切换、动态绑定和属性语义均有回归覆盖。未进行真实游戏帧耗时、分配/GC 或对象释放 profiling。

| external_property | 134.712 -> 114.737 ms，下降 14.8% | 159.138 -> 133.210 ms，下降 16.3% | 163.913 -> 157.434 ms，下降 4.0%，噪声边界 |
| list_property | 166.909 -> 139.464 ms，下降 16.5% | 196.270 -> 161.960 ms，下降 17.5% | 后续轮次未获得稳定收益 |

raw 快速路径获得最稳定的收益。`Expando` 在外部属性场景仍有一定正向结果，但外部方法和列表属性的重复测量不一致；保留它是因为实现范围较小、包装复用明确且语义测试完整，而不是宣称所有外部成员访问都已提速。真实游戏中应重点复核外部方法，若回退稳定重现，应移除 `Expando` 并仅保留 raw 快速路径。

## 步骤五（已完成）：结构化调用栈（普通函数快速路径已撤回）

完成日期：2026-11-02。

影响范围：`HTFunction` 的调用栈记录和错误输出，仍保留现有命名空间、解释器上下文与操作数栈模型。调用者上下文精简及调用帧存储合并未实施。

### 保留的实现

- 开启调用栈时保存 `HTStackTraceInfo`，包含函数引用、文件、行和列；只在 `processError()` 输出时通过 `toString()` 格式化，不再每次调用拼接字符串。
- 使用 `finally` 统一正常返回、提前返回和异常路径的出栈，错误输出完成后才移除当前函数。
- 多层 `processError()` 包装时保留最内层已经生成的完整堆栈，避免外层覆盖内层信息。实际抛出异常的函数现在会包含在堆栈中，并保持显示条数和顺序。
- 新增嵌套异常顺序、显示条数限制、异常后清空堆栈，以及可选位置参数、省略参数、闭包和 `this` 回归测试。

### 普通函数快速路径：已撤回

曾实现 `_callSimpleScript()`，覆盖非外部、非构造、非异步、非 variadic 且没有命名参数的函数。它复用现有调用命名空间和上下文，只减少通用 `_call()` 中的分支。

首轮 JIT 闭包样本改善 13.2%，但没有稳定复现。包含快速路径的完整测量中：

- JIT：`empty` 回退 1.6%，`identity` 改善 0.1%，`closure` 改善 2.9%，均未达到保留标准。
- AOT：`empty` 回退 2.9%，`identity` 改善 0.1%，`closure` 回退 4.4%。

该实现已完整撤回，通用函数语义测试继续保留。此结论不等于步骤九的 `call0` 无效：`call0` 是减少字节码解码和零参数集合组装的专用指令，与 Dart 侧函数入口快速路径处于不同层次；步骤九目前仍暂缓。

### 验证与实测结果

全量 `dart test` 共 455 项通过；修改文件的 `dart analyze` 无问题；JIT/AOT 基准均实际执行且校验值正确。

仅保留结构化堆栈后：

- JIT `stack_trace`：244.227 ms -> 225.697 ms，下降 7.6%。
- 交替 AOT `stack_trace`：273.520 ms -> 261.326 ms，下降 4.5%，接近噪声阈值。
- 普通 `identity` 在不同轮次中有正负有别的波动，未确认结构化堆栈对关闭堆栈的场景有稳定收益或回退。

结构化堆栈改善了错误语义并减少开启堆栈时的字符串分配，但应用级收益仍需在真实游戏的错误处理和帧耗时场景中复核。

## 后续行动范围：以编译期优化验收为起点

`plan_compile_time_optimization.md` 已经承接调用作用域、局部槽位、捕获 cell、模块声明缓存和有限常量折叠。本文不再重复这些设计，也不先实现字符串查找版轻量命名空间。

启动本文任一后续候选前，必须满足：

- 编译期计划各阶段已有明确的保留、撤回或未确认记录，全量测试、相关 analyze 和 AOT 实际执行通过。
- 以编译期计划完成后的提交重新建立 JIT/AOT 基线，不能沿用步骤一至五的旧耗时直接计算后续收益。
- 在真实 Flutter/Flame 游戏 profile 模式下重新确认热点、帧耗时和分配；如果编译期优化没有带来应用级改善，不继续扩大结构性改造。
- 每次只选择一个候选，不与字节码、调用作用域或操作数栈的其他改造混合测量。

在确有剩余热点时，推荐依次评估：稳定函数的直接 callee 缓存、`call0`/`call1`、共享操作数栈。这个顺序是评估顺序而不是必须全部执行的清单；前一项已覆盖热点或没有稳定收益时，应重新 profiling，而不是自动进入下一项。

由 `plan_compile_time_optimization.md` 的阶段一至三实施，包括独立词法解析器、轻量调用作用域、未捕获局部变量和闭包生命周期。`HTNamespace` 继续服务模块、类、struct、导入导出和动态回退。

本文件不再安排字符串版轻量命名空间，也不在没有生命周期证明时复用调用作用域。后续优化必须以该计划最终保留的实现为基线；如果其中某个阶段被撤回，应先重新评估依赖它的候选，而不是假定槽位或捕获 cell 已经存在。

## 步骤七（由其他计划承接）：局部变量槽位和捕获 cell

由编译期计划完成参数和局部变量的声明身份解析、slot 分配、真实捕获变量的 cell 表示，以及循环改写、动态回退、调试映射、字节码版本和预编译标准库更新。

本文件不再重复实施槽位化，也不自动追加符号 intern。若后续 profiling 仍显示非局部命名空间的字符串 key 是热点，应为符号表示单独建立有生命周期和失效测试的候选。

## 步骤八（条件执行）：稳定函数的直接 callee 缓存

影响范围：调用点和模块声明生命周期。第一版只考虑稳定顶层函数或模块函数，不同时引入成员内联缓存和 quickening。

### 启动条件

- 编译期计划阶段四没有覆盖剩余的调用点查找，且 profiling 仍显示稳定函数解析占明显成本。
- 如果阶段四已经保留直接声明缓存，先复用其模块代次、声明版本和失效机制；只有调用点仍有独立热点时才扩展，不重复增加一层缓存。

### 实施范围

- 缓存解析后的稳定 callee，减少递归和重复工具函数调用中的模块命名空间查找。
- 缓存必须校验所属模块和声明代次，生命周期不得超过对应 compilation 或模块声明。
- 动态赋值、删除、动态执行、导入、声明替换和模块重新执行必须失效或回退到通用路径。
- 类方法、成员访问和多态 receiver 不进入第一版，避免把 receiver 类型和继承失效问题混入稳定函数缓存。

### 验证与保留条件

覆盖声明替换、同名模块、模块重复执行、导入、动态赋值和删除，记录缓存项数量、命中、未命中和失效率。比较 `fib`、`identity`、`closure`、动态回退和外部绑定场景；只有正确性完整且 JIT/AOT 有重复收益时保留，否则撤回并保留通用查找。

## 步骤九（条件执行）：`call0` 和 `call1` 专用调用指令

影响范围：编译器、调用点字节码、解释器参数组装和预编译标准库。

### 启动条件

局部槽位和稳定 callee 解析之后，通用 `OpCode.call` 的静态信息解码、零参数或单参数集合组装仍是明确热点。步骤五撤回的 `_callSimpleScript()` 只是 Dart 函数入口分支优化，其测量结果不能代替对本步骤的判断。

### 实施范围

- 第一版仅增加 `call0` 和 `call1`，覆盖没有命名参数、spread 和构造调用标记的普通调用。
- 其他参数形式继续使用通用 `OpCode.call`，不改变默认参数、variadic、外部调用和错误语义。
- 同步字节码版本，并通过 `dart run utils/compile_hetu.dart` 重新生成预编译标准库。
- 固定多参数指令只有在 `call0`/`call1` 验收后仍有对应热点时另行评估。
- 本步骤不同时实施数值特化、类型化局部存储、superinstruction、peephole 或完整预解码指令流；常量折叠继续由编译期计划独立验收。

### 验证与保留条件

重点比较 `empty`、`identity`、`nested_callback`，同时确认 `named`、`variadic`、`spread`、构造调用和异常位置没有回退。记录编译耗时、字节码大小和额外内存；若仅有字节码变化而 JIT/AOT 没有稳定收益，保留简单通用指令。

### 零/单参数容器上限验证（已撤回）

在不改变字节码格式的前提下，曾验证普通脚本函数的零/单参数容器快速路径：零参数复用空 Map/List，单参数直接创建单元素 List，外部调用仍收到可修改的参数集合。参数绑定、普通函数和外部绑定专项测试共 20 项通过，修改文件的 `dart analyze` 通过。

同机 JIT 中，`empty` 中位数从 199485 µs 降为 182889 µs，但 `identity` 从 211109 µs 变为 213240 µs，`fib` 仅从 2875847 µs 降为 2798513 µs。AOT 中，`empty` 从 232235 µs 变为 232896 µs，`identity` 从 264076 µs 变为 265975 µs，`fib` 从 3766008 µs 降为 3724939 µs；随后两轮独立 AOT 可执行文件交替复测也没有稳定方向，差异均不足以达到保留标准。

候选实现已完整撤回。该结果只说明减少参数容器分配没有带来稳定的 AOT 收益，不证明绕过调用点缓存的独立 `call0`/`call1` 绝对无效；但当前证据不足以承担新增操作码、字节码版本和预编译标准库变更，因此不继续实施完整步骤九。只有新的 profile 明确指向缓存查询或静态信息解码时，才重新评估独立操作码原型。

## 步骤十（条件执行）：共享操作数栈

影响范围：解释器核心执行模型。只评估共享操作数栈，不把调用帧池化和逃逸分析作为同一改动。

### 启动条件

调用作用域、局部槽位和捕获 cell 已稳定，profiling 仍显示每个 `HTStackFrame` 的操作数列表分配或间接访问是主要成本。不得与前序未完成或尚未测量的字节码改造叠加。

### 实施范围

- 将每个 `HTStackFrame` 自带的操作数列表改为解释器级共享栈，调用帧保存 stack base、恢复位置和必要元数据。
- 保持现有返回值传播、局部符号记录、循环和 anchor 行为，明确每次执行结束的栈恢复边界。
- `FutureExecution` 必须保存和恢复完整栈区间及调用作用域，嵌套外部回调和重入执行不得覆盖仍存活的数据。
- 不池化调用帧，不复用仍可能被闭包或异步任务持有的栈区间。

### 验证与保留条件

除全量测试外，覆盖压力递归、深层表达式、提前返回、异常、异步挂起恢复、嵌套外部回调和长时间分配/GC。必须同时提供分配量、峰值内存和 JIT/AOT 耗时证据；如果复杂度明显增加而收益处于噪声范围，恢复每帧独立操作数栈。

## 步骤十一（场景驱动）：异步调度；尾调用继续暂缓

### 异步调度

只有真实应用存在大量立即完成或没有实际等待的异步脚本调用，且 profiling 指向 `Future(() => _call(...))` 调度成本时，才研究同步执行到第一个真正 `await` 的模型。

该方向应独立设计和验收，确认任务顺序、错误抛出时机、可重入和 `FutureExecution` 恢复行为。它不是普通函数调用的局部补丁，也不允许通过复用生命周期重叠的 context、frame 或栈区间换取收益。

### 尾调用

继续暂缓。尾调用只适用于明确的尾递归压力场景，会改变脚本调用栈和调试表现，当前 `fib` 等非尾递归热点不会受益。没有真实需求时不进入后续执行队列。

## 步骤十二（场景驱动）：替代执行模式和宿主级并行

### 静态脚本提前编译

对于随应用发布、运行期不修改且已被证明受解释器分派限制的脚本，可以独立研究构建期生成 Dart 代码或其他原生表示。它可能消除解释器分派，但不适合作为动态脚本的通用替代。

先以最小真实脚本验证闭包、动态类型、外部绑定、异步和错误语义，再决定是否扩大。必须提供两种执行模式的一致性测试、构建产物验证和端到端收益，不能只比较数值微基准。

### Isolate 并行

只面向相互独立、不共享 Flame UI 对象且确有吞吐需求的任务。它不能降低单次脚本调用延迟，应与函数调用优化分开评估，并计入对象传输、通信、生命周期和调试成本。

## 步骤十三（暂缓）：C/Rust 原生执行核心

当前不进入执行队列。只有存在明确且仍未满足的应用性能目标，profiling 又证明主要成本位于解释器核心而非外部绑定、对象包装或渲染时，才可评估最小原型。

原型只能先覆盖数值运算、局部变量和函数调用，用于测量收益上限；随后必须加入真实 Dart 绑定进行端到端比较，不能直接重写完整解释器。评估必须计入：

- Dart/Flame 对象的句柄和生命周期管理。
- 参数与返回值转换、字符串和集合复制。
- 脚本调用 Dart、Dart 再调用脚本的可重入状态。
- Future、事件循环、异常和 panic 的边界处理。
- Android、iOS、桌面和 Web 的构建分发差异。

## 持续暂缓的细分候选

以下项目不随上述步骤自动恢复：

- 原步骤五的调用者上下文精简，以及调用帧与结构化调用栈存储合并。步骤三的参数元数据曾因额外对象和间接访问出现整体回退，新的元数据改造必须有热点和分配证据。
- 类方法和成员内联缓存、运行时 quickening。
- 数值和布尔专用指令、类型化局部存储、superinstruction 和额外 peephole。
- 完整预解码指令流。
- 调用帧池化、逃逸分析和异步帧复用。
- 没有真实负载证明的符号 intern 和尾调用。

## 基准与验收

### 基线记录

- 记录编译期计划完成后的基线提交、各阶段保留或撤回状态、Dart SDK、机器和电源状态。
- 优化前后使用独立 AOT 可执行文件，在相同机器状态下交替运行；JIT 与 AOT 分开比较，不能互相外推。
